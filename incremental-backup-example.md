# Incremental filesystem backups with LsChanged and tar/gzip

This guide shows one way to create a weekly backup set with LsChanged and GNU `tar`:

- Sunday creates a complete backup of `/directory-for-backup/`.
- Monday through Saturday create compressed incremental archives containing files that were added or changed since the previous snapshot.
- Every incremental archive contains a deletion script. Run that script while restoring the archive to remove files that existed in the previous snapshot but have since been deleted.

The backup destination is `/backups/`.

## Prerequisites

Install or make available:

- `lschanged` in `PATH`.
- Bash.
- GNU `tar` with gzip support.
- A user that can read `/directory-for-backup/` and write `/backups/`.

The backup script records file metadata, not file contents, in an LsChanged store. A file is considered modified when its size, last-write time, file attributes, or Unix mode changes. LsChanged does not calculate content hashes.

## Backup script

Save the following as `/usr/local/sbin/lschanged-backup` and make it executable with `chmod 755 /usr/local/sbin/lschanged-backup`.

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

# The paths requested for this example.
SOURCE_DIRECTORY='/directory-for-backup/'
BACKUP_DIRECTORY='/backups/'
STORE_DIRECTORY="${BACKUP_DIRECTORY}.lschanged-store"

# Override this if lschanged is installed somewhere not in PATH.
LSCHANGED_COMMAND="${LSCHANGED_COMMAND:-lschanged}"

# GNU tar is used because the script supplies multiple -C directories and
# reads the list of files generated by lschanged.
TAR_COMMAND="${TAR_COMMAND:-tar}"

DATE="$(date '+%Y-%m-%d')"
DAY_OF_WEEK="$(date '+%u')" # 1 = Monday, ..., 7 = Sunday
WORK_DIRECTORY="$(mktemp -d /tmp/lschanged-backup.XXXXXX)"
ADDED_OR_MODIFIED_LIST="$WORK_DIRECTORY/added-or-modified.txt"
DELETED_LIST="$WORK_DIRECTORY/deleted.txt"
DELETION_SCRIPT="$WORK_DIRECTORY/deletions.sh"
DELETION_SCRIPT_NAME='deletions.sh'

cleanup() {
	rm -rf -- "$WORK_DIRECTORY"
}
trap cleanup EXIT

fail() {
	printf 'lschanged-backup: %s\n' "$*" >&2
	exit 1
}

[[ -d "$SOURCE_DIRECTORY" ]] || fail "Source directory does not exist: $SOURCE_DIRECTORY"
mkdir -p -- "$BACKUP_DIRECTORY"
mkdir -p -- "$STORE_DIRECTORY"

if [[ "$DAY_OF_WEEK" == '7' ]]; then
	# Start a new weekly snapshot history. The full archive is created before
	# scanning so that the snapshot describes the contents included in it.
	FULL_ARCHIVE="$BACKUP_DIRECTORY/full-$DATE.tar.gz"

	"$TAR_COMMAND" \
		--create \
		--gzip \
		--file "$FULL_ARCHIVE" \
		--directory "$SOURCE_DIRECTORY" \
		.

	"$LSCHANGED_COMMAND" clear -s "$STORE_DIRECTORY"
	"$LSCHANGED_COMMAND" scan "$SOURCE_DIRECTORY" -s "$STORE_DIRECTORY"

	printf 'Created full backup: %s\n' "$FULL_ARCHIVE"
	exit 0
fi

# The first weekday backup requires Sunday's full backup and snapshot.
SNAPSHOT_LIST="$WORK_DIRECTORY/snapshots.txt"
if ! "$LSCHANGED_COMMAND" list -s "$STORE_DIRECTORY" >"$SNAPSHOT_LIST" 2>/dev/null; then
	fail "Cannot read the LsChanged store; run the Sunday full backup first"
fi
if ! grep -q '[0-9]' "$SNAPSHOT_LIST"; then
	fail "The LsChanged store has no snapshot; run the Sunday full backup first"
fi

# Add the current filesystem state to the store. The new snapshot is then
# compared with the previous one.
"$LSCHANGED_COMMAND" scan "$SOURCE_DIRECTORY" -s "$STORE_DIRECTORY"

run_compare() {
	local states="$1"
	local output_file="$2"
	local exit_code

	set +e
	"$LSCHANGED_COMMAND" compare lp "$states" "$output_file" \
		-rp "$SOURCE_DIRECTORY" \
		-s "$STORE_DIRECTORY"
	exit_code=$?
	set -e

	# LsChanged returns 1 when the comparison is valid but no paths matched.
	if [[ "$exit_code" != 0 && "$exit_code" != 1 ]]; then
		fail "LsChanged comparison failed with exit code $exit_code"
	fi
}

# Relative paths are used so the archive can be restored below the original
# source directory or another chosen target directory.
run_compare 'am' "$ADDED_OR_MODIFIED_LIST"
run_compare 'd' "$DELETED_LIST"

INCREMENTAL_ARCHIVE="$BACKUP_DIRECTORY/incremental-$DATE.tar.gz"

# An incremental archive always contains deletions.sh, even when no files were
# deleted. This makes every daily archive self-describing during restoration.
{
	printf '%s\n' '#!/usr/bin/env bash'
	printf '%s\n' '# Generated by lschanged-backup.'
	printf '%s\n' 'set -Eeuo pipefail'
	printf '%s\n' "BACKUP_TARGET=\"\${BACKUP_TARGET:-/directory-for-backup/}\""
	printf '%s\n' 'remove_path() { rm -f -- "$BACKUP_TARGET/$1"; }'

	while IFS= read -r path; do
		[[ -n "$path" ]] || continue

		# %q produces a Bash-safe argument, including for spaces and shell
		# metacharacters in a relative path.
		printf -v quoted_path '%q' "$path"
		printf 'remove_path %s\n' "$quoted_path"
	done <"$DELETED_LIST"
} >"$DELETION_SCRIPT"
chmod 755 "$DELETION_SCRIPT"

# -T reads the relative file list while -C changes to the source directory.
# The second -C adds the generated deletion script to the same gzip archive.
"$TAR_COMMAND" \
	--create \
	--gzip \
	--file "$INCREMENTAL_ARCHIVE" \
	--directory "$SOURCE_DIRECTORY" \
	--verbatim-files-from \
	--files-from "$ADDED_OR_MODIFIED_LIST" \
	--directory "$WORK_DIRECTORY" \
	"$DELETION_SCRIPT_NAME"

printf 'Created incremental backup: %s\n' "$INCREMENTAL_ARCHIVE"
```

## How the script works

The script keeps LsChanged's snapshot store at `/backups/.lschanged-store`:

1. On Sunday, it creates `/backups/full-YYYY-MM-DD.tar.gz`, clears the previous snapshot history, and records the full backup's state.
2. On a weekday, it scans the source again and compares the new snapshot with the previous one.
3. `compare lp am` writes added and modified relative paths to a temporary file. Those files are placed in the incremental archive.
4. `compare lp d` writes deleted relative paths to a second temporary file.
5. The deleted paths are converted into `remove_path` commands in `deletions.sh`.
6. The incremental archive contains both the changed files and `deletions.sh`.

A weekday archive is created even when there are no changed files, because it still contains the deletion script. LsChanged's exit code `1` means that a valid comparison produced no paths; the script treats that as a successful backup day.

The script intentionally creates the Sunday archive before taking the Sunday scan. This keeps the full archive and its baseline snapshot as close together as possible. As with any filesystem backup, files changed while the archive is being created can produce an inconsistent point-in-time backup; quiesce applications or use a filesystem snapshot if strict consistency is required.

## Restore procedure

Restore the full archive first, then apply incremental archives in date order. Run each deletion script after extracting its corresponding archive so that deletions are applied at the correct point in the sequence.

For example:

```bash
mkdir -p /restore-target

tar --extract --gzip \
	--file /backups/full-2026-08-23.tar.gz \
	--directory /restore-target

tar --extract --gzip \
	--file /backups/incremental-2026-08-24.tar.gz \
	--directory /restore-target
BACKUP_TARGET=/restore-target /restore-target/deletions.sh

# Repeat extraction and deletion-script execution for each later archive.
```

The full archive contains the source directory contents without an additional top-level directory because it is created with `tar --directory /directory-for-backup/ .`. Incremental archive entries use paths relative to that directory.

To inspect an archive without extracting it:

```bash
tar --list --gzip --file /backups/incremental-2026-08-24.tar.gz
```

Review generated deletion scripts before executing them, especially when restoring into a location other than `/directory-for-backup/`.

## Scheduling with cron

Install the script and make sure the cron service account can access both paths:

```bash
sudo install -o root -g root -m 0755 lschanged-backup /usr/local/sbin/lschanged-backup
sudo mkdir -p /backups/
```

Edit root's crontab:

```bash
sudo crontab -e
```

Run the backup every night at 02:00:

```cron
0 2 * * * /usr/local/sbin/lschanged-backup >>/var/log/lschanged-backup.log 2>&1
```

The script determines whether the run is a Sunday or weekday from the system date, so the same cron entry performs the full and incremental jobs automatically. If the machine is powered off at 02:00, ordinary cron may skip that run; use a systemd timer with a persistent setting or another scheduler with missed-run support if that matters.

## Operational recommendations

- Protect `/backups/` from unauthorized modification because it contains both backup data and deletion scripts.
- Copy completed archives to separate storage; a backup on the same disk does not protect against disk failure.
- Keep at least one complete Sunday archive and all following incremental archives needed to reach the desired recovery date.
- Test restoration regularly, including execution of deletion scripts in a temporary restore directory.
- Do not run two instances of the script for the same backup set at the same time. If concurrent invocations are possible, add an external lock such as `flock` around the cron command.
- The path format is line-oriented. Files with unusual names containing newline characters are not suitable for this example because LsChanged reports one path per line.
